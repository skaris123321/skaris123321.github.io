# Документ требований: Интеграция оплаты через СБП

## Введение

Данный документ определяет требования к интеграции функционала оплаты через QR-код СБП (Система Быстрых Платежей) в интернет-магазин РОСЭК. Система заменит текущий QR-код-заглушку на реальную обработку платежей, проверит завершение оплаты и отправит заказ в 1С только после подтверждения успешной оплаты.

## Глоссарий

- **СБП**: Система Быстрых Платежей - национальная платежная система для мгновенных переводов
- **Генератор_QR**: Компонент, отвечающий за генерацию QR-кодов, совместимых с СБП
- **Монитор_Платежей**: Компонент, проверяющий статус платежа через опрос или вебхуки
- **Обработчик_Заказов**: Компонент, обрабатывающий отправку заказа в 1С после подтверждения оплаты
- **Модальное_Окно_Оплаты**: UI-компонент, отображающий QR-код и статус платежа
- **1С**: Система управления предприятием для обработки заказов
- **Физ_Лицо**: Физическое лицо, совершающее покупку
- **Юр_Лицо**: Юридическое лицо, совершающее покупку

## Требования

### Требование 1: Генерация QR-кода

**Пользовательская история:** Как покупатель, я хочу видеть настоящий QR-код СБП с суммой моего заказа, чтобы я мог завершить оплату через мобильное приложение банка.

#### Критерии приемки

1. КОГДА покупатель отправляет форму заказа, Генератор_QR ДОЛЖЕН создать QR-код, совместимый с СБП, содержащий сумму платежа и детали заказа
2. КОГДА генерируется QR-код, Генератор_QR ДОЛЖЕН включить уникальный идентификатор платежа для отслеживания
3. КОГДА генерируется QR-код, Генератор_QR ДОЛЖЕН включить информацию о продавце и ссылку на заказ
4. Модальное_Окно_Оплаты ДОЛЖНО отобразить сгенерированный QR-код в течение 2 секунд после отправки заказа
5. КОГДА отображается QR-код, Модальное_Окно_Оплаты ДОЛЖНО показать сумму платежа, номер заказа и время истечения

### Требование 2: Мониторинг статуса платежа

**Пользовательская история:** Как покупатель, я хочу видеть обновления статуса платежа в реальном времени, чтобы знать, когда моя оплата подтверждена.

#### Критерии приемки

1. КОГДА отображается QR-код, Монитор_Платежей ДОЛЖЕН начать проверку статуса платежа каждые 3 секунды
2. КОГДА статус платежа меняется на подтвержденный, Монитор_Платежей ДОЛЖЕН немедленно уведомить Обработчик_Заказов
3. КОГДА статус платежа меняется, Модальное_Окно_Оплаты ДОЛЖНО обновить интерфейс для отражения текущего статуса
4. ПОКА платеж находится в ожидании, Модальное_Окно_Оплаты ДОЛЖНО отображать индикатор загрузки с текстом статуса
5. ЕСЛИ получено подтверждение платежа, ТО Модальное_Окно_Оплаты ДОЛЖНО отобразить сообщение об успехе

### Требование 3: Обработка истечения времени платежа

**Пользовательская история:** Как покупатель, я хочу знать, если истекло время для оплаты, чтобы я мог запросить новый QR-код при необходимости.

#### Критерии приемки

1. КОГДА генерируется QR-код, Система ДОЛЖНА установить время истечения 15 минут
2. КОГДА время истечения достигнуто без оплаты, Монитор_Платежей ДОЛЖЕН прекратить опрос
3. ЕСЛИ происходит истечение времени платежа, ТО Модальное_Окно_Оплаты ДОЛЖНО отобразить сообщение об истечении с опцией перегенерации QR-кода
4. КОГДА покупатель запрашивает перегенерацию QR-кода, Система ДОЛЖНА сгенерировать новый QR-код с новым идентификатором платежа
5. КОГДА происходит истечение времени, Система ДОЛЖНА записать в лог незавершенную попытку оплаты с деталями заказа

### Требование 4: Отправка заказа после оплаты

**Пользовательская история:** Как владелец бизнеса, я хочу, чтобы заказы отправлялись в 1С только после подтверждения оплаты, чтобы не обрабатывать неоплаченные заказы.

#### Критерии приемки

1. КОГДА статус платежа подтвержден, Обработчик_Заказов ДОЛЖЕН отправить данные заказа в 1С через существующий endpoint /api/orders
2. Обработчик_Заказов НЕ ДОЛЖЕН отправлять данные заказа в 1С до подтверждения оплаты
3. КОГДА отправляется в 1С, Обработчик_Заказов ДОЛЖЕН включить детали подтверждения платежа и ID транзакции
4. КОГДА отправка в 1С успешна, Система ДОЛЖНА отправить подтверждающее письмо покупателю
5. ЕСЛИ отправка в 1С не удалась после оплаты, ТО Система ДОЛЖНА повторить отправку до 3 раз с экспоненциальной задержкой

### Требование 5: Поддержка типов клиентов

**Пользовательская история:** Как покупатель, я хочу, чтобы оплата работала как для физических, так и для юридических лиц, чтобы я мог оплатить независимо от типа клиента.

#### Критерии приемки

1. КОГДА Физ_Лицо отправляет заказ, Генератор_QR ДОЛЖЕН создать QR-код с деталями платежа для физического лица
2. КОГДА Юр_Лицо отправляет заказ, Генератор_QR ДОЛЖЕН создать QR-код с деталями платежа для юридического лица
3. Система ДОЛЖНА включать соответствующую информацию о клиенте (ИНН, КПП для юридических лиц) в метаданные платежа
4. КОГДА платеж подтвержден, Обработчик_Заказов ДОЛЖЕН сохранить информацию о типе клиента при отправке в 1С
5. Модальное_Окно_Оплаты ДОЛЖНО отображать инструкции по оплате, соответствующие типу клиента

### Требование 6: Обработка ошибок

**Пользовательская история:** Как покупатель, я хочу видеть понятные сообщения об ошибках при неудачной оплате, чтобы понимать, что пошло не так и что делать дальше.

#### Критерии приемки

1. ЕСЛИ генерация QR-кода не удалась, ТО Система ДОЛЖНА отобразить сообщение об ошибке и предоставить опцию повтора
2. ЕСЛИ проверка статуса платежа не удалась, ТО Монитор_Платежей ДОЛЖЕН повторить попытку до 5 раз перед показом ошибки
3. КОГДА происходит ошибка платежа, Модальное_Окно_Оплаты ДОЛЖНО отобразить понятное сообщение об ошибке с контактной информацией поддержки
4. ЕСЛИ платеж отклонен банком, ТО Система ДОЛЖНА отобразить причину отклонения и предложить сгенерировать новый QR-код
5. КОГДА происходит любая ошибка, Система ДОЛЖНА записать детальную информацию об ошибке для отладки

### Требование 7: Сохранение статуса платежей

**Пользовательская история:** Как владелец бизнеса, я хочу, чтобы попытки оплаты записывались, чтобы я мог отслеживать и сверять платежи.

#### Критерии приемки

1. КОГДА генерируется QR-код, Система ДОЛЖНА сохранить детали попытки оплаты в локальное хранилище
2. КОГДА статус платежа меняется, Система ДОЛЖНА обновить сохраненную запись о платеже
3. Система ДОЛЖНА хранить записи о платежах, включая: временную метку, детали заказа, ID платежа, статус и ID транзакции
4. КОГДА платеж подтвержден, Система ДОЛЖНА отметить запись о платеже как завершенную с временной меткой подтверждения
5. Система ДОЛЖНА хранить записи о платежах минимум 30 дней для сверки

### Требование 8: Обновления пользовательского интерфейса

**Пользовательская история:** Как покупатель, я хочу понятный и интуитивный интерфейс оплаты, чтобы я мог легко завершить платеж.

#### Критерии приемки

1. КОГДА открывается модальное окно оплаты, Модальное_Окно_Оплаты ДОЛЖНО отображать QR-код на видном месте в центре
2. Модальное_Окно_Оплаты ДОЛЖНО отображать инструкции по оплате на русском языке с понятными шагами
3. ПОКА платеж находится в ожидании, Модальное_Окно_Оплаты ДОЛЖНО показывать таймер обратного отсчета до истечения QR-кода
4. КОГДА платеж подтвержден, Модальное_Окно_Оплаты ДОЛЖНО отобразить анимацию успеха и подтверждающее сообщение
5. Модальное_Окно_Оплаты ДОЛЖНО предоставить кнопку "Отмена", которая закрывает окно и возвращает в корзину

### Требование 9: Интеграция с API СБП

**Пользовательская история:** Как разработчик, я хочу правильно интегрироваться с API СБП, чтобы платежи обрабатывались надежно.

#### Критерии приемки

1. Система ДОЛЖНА использовать официальный API СБП для генерации QR-кодов
2. Система ДОЛЖНА аутентифицироваться с API СБП, используя безопасные учетные данные, хранящиеся в переменных окружения
3. КОГДА вызывается API СБП, Система ДОЛЖНА включать все обязательные параметры согласно спецификации СБП
4. Система ДОЛЖНА корректно обрабатывать ограничения скорости API СБП с соответствующей логикой повторов
5. Система ДОЛЖНА валидировать ответы API СБП перед обработкой обновлений статуса платежа

### Требование 10: Безопасность и защита данных

**Пользовательская история:** Как покупатель, я хочу, чтобы мои платежные данные были защищены, чтобы моя финансовая информация была в безопасности.

#### Критерии приемки

1. Система ДОЛЖНА передавать все платежные данные только через HTTPS-соединения
2. Система НЕ ДОЛЖНА хранить банковские учетные данные клиентов или информацию о картах
3. Система ДОЛЖНА хранить учетные данные API СБП в переменных окружения, а не в коде
4. КОГДА логируется информация о платеже, Система НЕ ДОЛЖНА логировать конфиденциальные платежные данные
5. Система ДОЛЖНА валидировать все обратные вызовы о платежах для предотвращения мошеннических подтверждений платежей
